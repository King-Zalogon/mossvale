## Research applied to this game

These are primary references actually consulted, not imported dependencies. The recommendations below are our application to Mossvale; they are not endorsements of this implementation by the authors.

| Reference | What it teaches | Concrete application |
| --- | --- | --- |
| Cure, [The Pixel Art Tutorial](https://pixeljoint.com/forum/forum_posts.asp?TID=11299) (2010), especially clusters, noise and palette ramps | Deliberate connected shapes communicate form; isolated detail easily becomes noise. | Replace the bright repeated flecks of the terrain fixture with quieter base surfaces and sparse meaningful clusters. Check sprites at their normal draw size before adding detail. |
| [Liberated Pixel Cup style guide](https://lpc.opengameart.org/static/LPC-Style-Guide/build/styleguide.html), perspective, light, tile authoring and characters | Shared perspective/light conventions and restrained center-tile texture make independently authored assets cohere. | Define Mossvale's own light, pixel density, palette hierarchy and anchor contract. LPC is top-down: its camera/grid/body specifications must not be copied into this isometric game. |
| [Tiled terrain documentation](https://docs.mapeditor.org/en/stable/manual/terrain/) | Terrain sets match corners, edges or both; reduced mixed sets can cover blob transitions. Decorative variations have explicit probabilities. | #96 must author and review convex and concave shore/path variants, narrow paths and bridge contacts. A line drawn on a tile boundary does not fulfill the art requirement. Preserve explicit collision data and seeded selection. |
| [Flare tile-set definitions](https://github.com/flareteam/flare-engine/wiki/Tile-Set-Definitions) and [map creation](https://github.com/flareteam/flare-engine/wiki/Creating-a-New-Map-with-the-FLARE-art-assets) | Isometric tiles use explicit image rectangles/offsets, with variations assembled in maps. | Keep reusable tile sources and ground anchors in the existing manifest/compiler. Test repeated areas and contacts in a scene. Study structure without adopting Flare's prerendered look or importing its assets. |
| [Tuxemon](https://github.com/Tuxemon/Tuxemon), source inspected at `9e6258ff726b786040a267e8bdbbf037b560285e`, [WorldState](https://github.com/Tuxemon/Tuxemon/blob/9e6258ff726b786040a267e8bdbbf037b560285e/tuxemon/states/world_state.py) | Its world state has separate input processing, update and renderer calls; a monster RPG is composed as a playable flow, not isolated art sheets. | Evaluate exploration → interaction → encounter → battle → reward → exploration through actual controls. Retain Mossvale's existing domain/controller split rather than replacing its engine. |
| Robert Nystrom, [Game Programming Patterns: Game Loop](https://gameprogrammingpatterns.com/game-loop.html) | Input processing, simulation and rendering have different responsibilities and should keep responding. | Treat a change of movement input as presentation/input state. Release held movement on takeover; do not encode the HUD mode in adventure saves. |
| Jesse Schell, [The Art of Game Design: A Book of Lenses](https://schellgames.com/art-of-game-design/) | Its design method evaluates the player's experience through different questions. The public book overview was consulted; this is not a claim to have read the full book during the audit. | Require a scene's purpose, useful player action, consequence and next goal; a reward persistence assertion alone does not establish an interesting scene (#237/#244). |
| [Game Accessibility Guidelines: simple controls](https://gameaccessibilityguidelines.com/ensure-controls-are-as-simple-as-possible-or-provide-a-simpler-alternative/) | Controls should impose as little avoidable complexity as possible. | Present the active movement method and relevant instructions, keep touch targets usable and preserve focus when controls disappear. |

No reference artwork or code was imported. Tuxemon's README identifies GPL code; LPC publishes specific licenses; Flare assets and code require their own license checks. Before any reuse, inspect the exact file's license/attribution and project compatibility. Reference access is not permission to copy Pokémon or another game's art.

## Findings from the actual scene and source

| Finding | Evidence in current implementation | Required next work |
| --- | --- | --- |
| Ground and props do not form a consistent art system. Ground uses flat per-cell diamonds and small marks; props have much richer shape/shading. | `dist/src/render/world.js`, the ground loop; `dist/src/data/assets.js`; the Sunlit Trail captures below. | #96: coherent shared ground art with quieter colors, worn paths, bank depth and corner transitions. Evaluate together with the red-cap player, an NPC, trees and cottage at normal zoom. |
| The fixture announces its grid instead of hiding it. It repeats bright grass details, hard diamonds and straight outlined water rectangles. | `dist/assets/terrain-family/*.svg`, `dist/src/ui/terrain-family-preview.js`; the owner's screenshot of PR #233. | Replace the art/transition treatment, then show an irregular shoreline and winding path in a playable scene. Enlarging the fixture does not fix its composition. |
| Desktop movement controls were selected from screen width/coarse capability rather than actual movement input. Hybrid users could see both touch controls and keyboard hints. | `dist/style.css` width/coarse rules; previously no input mode in `dist/src/input.js`. | #241 correction in this branch: initial primary-pointer choice, then real touch/pen, mouse or movement-key input; hidden controls leave the focus/accessibility tree. |
| Short landscape guidance can sit over the character while dialogue and findings compete for space. | `.toast`, `.environment-message`, `.speech-bubble`; the phone-landscape capture. | #238 owns guidance/discovery hierarchy; #236 owns the bottom dialogue panel. Recheck both together after integration. |
| Movement and identity are not consistently convincing even when frames/anchors validate. | Owner reports in #239/#240; existing separate motion/follower atlases. | Neutral standing poses and the accepted Voltkit identity require visual/source corrections, not more technical acceptance labels. |
| The full scene still needs authored purpose and legible moment-to-moment feedback. | Owner reports in #237 and #245; current map/battle/scene proof flow. | Build #245's ten-minute slice, including an encounter, useful reward and clear next goal. Judge #173/#229 in that flow before increasing breadth. |

## Art and presentation bar for the next slice

Keep the existing 2:1 isometric projection, eight directions, `56×28` world tile footprint and stable manifest IDs. Retain the red-cap identity and each approved creature design. Specify source pixel density, palette/light references, apparent object scale and foot anchors before generating a batch. A bigger source image or more colors is not an improvement by itself.

Terrain must recede behind characters and interactions: calm centers, controlled detail density, distinguishable materials, softened path contacts and banks with depth. Use neighbor-selected art for outside/inside corners, not outline strokes around every water cell. Review tile repetition and negative space at normal camera zoom. Changes to perceived walkability must be checked against existing collision and route accessibility.

A scene review includes the playable route, actor/prop grouping, player and target visibility, UI priority and story purpose. An animation review includes walk, run, turn and stop; combat includes anticipation, target, impact and recovery, with a readable reduced-motion alternative. Source/reference consistency and technical checks remain mandatory but are separate from these visual and content decisions.

Review at 1366×768 desktop, 390×844 portrait and 844×390 landscape, including fullscreen where supported. Preserve captures and a short actual-control recording for the complete #245 slice. A tiny compiler fixture and a large atlas contact sheet are supporting diagnostics, not substitutes. This audit does not claim that the complete game now meets this bar.

## #241 implementation and evidence

The initial movement HUD follows the primary pointer. Actual touch/pen presses reveal the pad and Run; mouse presses and keyboard movement select desktop controls. A hybrid with both fine/coarse capabilities can keep a clear desktop playfield. Menu/reading navigation does not switch the movement method. Changing method releases held touch/key movement and returns focus from a hidden movement button to the game. The existing run preference is preserved. Width/orientation remain layout inputs, not the movement-method decision.

[Hybrid desktop before](quality-review/241-desktop-before.png) · [Hybrid desktop after](quality-review/241-desktop-after.png) · [Phone portrait](quality-review/241-phone-portrait.png) · [Phone landscape](quality-review/241-phone-landscape.png). Desktop captures use a 1366×1000 browser so the full existing playfield/footer can be seen at its normal CSS scale; the regression also checks a 600 px desktop window. Portrait and landscape captures use the actual sizes stated above. The before capture serves the exact baseline versions of input, stylesheet and HTML from integration `748c887`; other scene assets are unchanged.

`tests/input-mode.browser.mjs` drives real keyboard movement, touch drag, keyboard takeover of a captured touch and mouse/touch switching. Fine/coarse hybrid capability is deliberately emulated because Chromium exposes only one emulated primary pointer; this is not a claim of testing physical Windows hybrid hardware. `tests/responsive-journal.browser.mjs` covers orientation, interrupted dragging and fullscreen; the existing follower and obstacle tests switch to actual touch before using the pad.

Run `npm run verify`, `npm run build` and catalogue impact on the final branch before integration. Local evidence does not establish green remote CI, full #245 completion or owner visual approval of the remaining art. No production deployment is part of this work.
